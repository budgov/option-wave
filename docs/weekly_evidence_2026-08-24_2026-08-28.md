# Weekly model evidence: 2026-08-24 through 2026-08-28

This note records aggregate model evidence only. It intentionally excludes
broker credentials, account data, Telegram content, raw market records,
runtime databases, logs, and machine-specific paths.

## Decision

The production model is **not promoted or reweighted** from this week's
results. The 30-minute challenger did not beat a constant 50% probability
baseline, and only two independent sessions met the complete-day training
gate. The correct action is to preserve the champion, improve causal data
quality and abstention behavior, and continue collecting shadow evidence.

The observed probability range was close to 0.5 while many expected moves
were below estimated trading friction. A forced `up` or `down` label therefore
overstates what the model knows. Raw probabilities and numerical forecasts
must remain available for scoring, but weak or incomplete evidence must be
reported as non-actionable.

## Required production boundaries

1. **Causal labels:** a maturity label is accepted only from the nearest quote
   within plus or minus five seconds of its target timestamp. A later minute
   quote must not be substituted for a missing point-in-time observation.
2. **Invalid-day isolation:** an incomplete or invalidated session may be
   scored for diagnostics, but it must not update durable calibration or model
   state. Shadow calibration is rebuilt from complete, officially closed,
   non-invalidated sessions.
3. **Anomalous-chain isolation:** impossible quotes, invalid Greeks or OI, bad
   contract matches, and extreme GEX observations are quarantined before any
   ELO, covariance, previous-chain, or GEX-history mutation.
4. **Separate semantics:** evidence quality, directional probability, and
   trade actionability are distinct fields. Evidence quality is not a win
   probability.
5. **Explicit abstention:** preserve raw probability and expected return while
   emitting an actionable decision and reasons. Probability too close to 0.5,
   insufficient evidence or feature completeness, invalid training-day state,
   and an edge below spread and fee pressure all require abstention.
6. **Conservative calibration:** calibrated probability remains shadow-only
   and shrinks uncertain estimates toward 0.5. Two valid sessions cannot
   authorize a production-weight change.
7. **Contract-value shadow layer:** Delta, Gamma, Theta, Vega/IV stress,
   holding period, executable spread, multiplier, and fees are evaluated only
   when their units and quote provenance are explicit. Missing or ambiguous
   inputs produce an auditable abstention and do not alter the legacy score.
8. **Bounded state:** checkpoints retain only model state, the compact previous
   chain needed for OI deltas, bounded GEX history, and compact Fourier
   summaries. Full chains and FFT arrays do not belong in repeated forecast
   payloads.

## Promotion gate

Twenty complete valid trading days is the minimum statistical floor requested
for reconsideration, not the deployment threshold. The current operational
gate is deliberately stricter: a challenger remains shadow-only until there
are at least **40 complete valid trading days** and **500 mature forecast
origins per symbol**. Promotion additionally requires purged day-level
walk-forward evidence that the challenger:

- beats the constant 50% baseline on both Brier score and log loss;
- improves QQQ and SPY separately rather than hiding weakness in one symbol;
- remains positive after point-in-time bid/ask, fees, and slippage stress;
- has sensible probability calibration and interval coverage;
- remains stable after removing any one day and across distinct regimes; and
- does not learn from quarantined chains, invalid sessions, or labels outside
  the target-time tolerance.

Meeting the day count alone is not sufficient. The challenger must actually
beat the champion/baseline under these gates before a reviewed, reversible
promotion.

## Reproducible verification

From the repository root on Windows:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m benchmarks.benchmark_ocean_wave --iterations 100
```

The standalone C++ tests can be built from an x64 MSVC developer environment
with the same hardening flags as the extension:

```powershell
cl.exe /nologo /std:c++17 /O2 /W4 /EHsc /permissive- /sdl /guard:cf /Icpp tests\cpp_kernel_smoke.cpp /Fe:$env:TEMP\ocean-wave-cpp-kernel-test.exe /link /DYNAMICBASE /NXCOMPAT /guard:cf
& $env:TEMP\ocean-wave-cpp-kernel-test.exe
cl.exe /nologo /std:c++17 /O2 /W4 /EHsc /permissive- /sdl /guard:cf /Icpp tests\cpp_fourier_features_test.cpp /Fe:$env:TEMP\ocean-wave-cpp-fourier-test.exe /link /DYNAMICBASE /NXCOMPAT /guard:cf
& $env:TEMP\ocean-wave-cpp-fourier-test.exe
```

Validate the deployed extension against the SHA-256 recorded in the approved
release manifest (do not substitute an unreviewed self-computed digest):

```powershell
.\.venv\Scripts\python.exe scripts\validate_native_core.py --extension option_wave\_core.cp312-win_amd64.pyd --expected-sha256 <approved-sha256>
```

The integrated release check completed 75 Python tests and both C++
executables. Native validation reported `parity=bit_exact` for the two native
entry points (`forecast_surface` and `evolve_field`) on its fixed fixture, and
`intraday_fourier=causal_v2`. A separate regression now proves exact equality
at the canonicalized public forecast boundary between the native forecast
path and the Python fallback: trend, confidence, probabilities, expectations,
grids, surfaces and public diagnostics are compared exactly. This statement
does not claim that every internal factor-extraction object is bit-exact; those
implementation diagnostics can legitimately differ before the public
boundary. A compiled 2,020-row warm-path run measured 14.272 ms median and
15.166 ms p95 over 200 iterations. Benchmark values are environment-sensitive
and should be compared only under the same controlled conditions.

SQLite integrity belongs to the host integration, not this library: this
repository does not own or ship a runtime database. The host's release check
must use a read-only or copy-based `PRAGMA integrity_check` and
`PRAGMA foreign_key_check` without checkpointing or modifying a live WAL.
